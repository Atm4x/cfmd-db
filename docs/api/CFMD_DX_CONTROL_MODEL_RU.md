# Модель управления внешним интерфейсом CFMD

## Зачем этот документ

CFMD уже имеет сильное математическое и транзакционное ядро, но сильное ядро не оправдывает сложный прикладной интерфейс. Для обычного разработчика должно быть очевидно:

1. над какой базой или какой зафиксированной ревизией выполняется действие;
2. какие данные или изменения участвуют в действии;
3. является ли операция только описанием намерения или реально меняет базу;
4. в какой строке происходит публикация изменения;
5. где искать содержимое атомарной операции при ревью кода.

P354 фиксирует это как правило архитектуры внешнего интерфейса, а не как вопрос именования методов.

## Главное правило

Объект, который **описывает** действие, не должен сам становиться объектом власти над базой.

Поэтому:

- `Query` описывает чтение;
- `Plan` описывает низкоуровневое изменение;
- `Transaction` хранит совокупность изменений одной исходной ревизии;
- `Candidate` описывает точный будущий мир;
- `Database` или `SessionDatabase` владеет публикацией в живую базу;
- `ReadContext` владеет чтением конкретной ревизии;
- `Watch` владеет только жизненным циклом уже созданной подписки, но не властью над базой.

Из этого следует простой критерий ревью: строка, которая меняет живую базу, должна прямо называть базу.

Хорошо:

```rust
let preview = db.preview(&tx)?;
let outcome = db.commit(&tx)?;
```

Плохо:

```rust
let preview = tx.preview()?;
tx.commit()?;
```

Во втором варианте строка скрывает, над какой базой выполняется действие. Чтобы восстановить смысл, надо искать место создания `tx` и помнить скрытую связь объекта с базой.

## Что изменено в P354

### Транзакция стала пассивным контейнером

`Transaction` больше не имеет публичных `preview`, `candidate` и `commit`.

Она умеет:

- хранить идентификатор атомарной операции;
- помнить точную исходную ревизию;
- давать чтение из этой исходной ревизии;
- принимать совместимые изменения через `add`;
- сообщать, пустая она или нет;
- при необходимости превращаться в низкоуровневый `Plan`.

Она не умеет сама менять базу.

Обычный adaptive-синтаксис:

```rust
let mut tx = Transaction::new();
db.todos.add(&mut tx, first)?;
db.todos.add(&mut tx, second)?;

let preview = db.preview(&tx)?;
let outcome = db.commit(&tx)?;
```

Если приложению нужен внешний/recoverable idempotency key, он настраивается на той же пассивной транзакции до формирования intent и не привязывает её к текущему HEAD:

```rust
let mut tx = Transaction::new()
    .with_idempotency_key(TransactionId::new(42))?;
db.todos.add(&mut tx, first)?;
db.commit(&tx)?;
```

Конечные строки читаются без знания внутреннего устройства `Transaction`:

- `db.preview(&tx)` — показать, что транзакция `tx` сделает с `db`;
- `db.commit(&tx)` — атомарно опубликовать `tx` в `db`.

### `Candidate` больше не публикует себя

`Candidate` — это предложенный будущий мир. Он полезен для:

- чтения будущего состояния;
- диагностики;
- подсчёта прямых и производных эффектов;
- предварительного просмотра;
- Studio и других инструментов.

Но `Candidate` больше не имеет публичного пути публикации. Это устраняет второй скрытый путь изменения базы.

### Низкоуровневая публикация названа явно

Для инструментов, протокола и привязок остаётся:

```rust
db.commit_plan(&plan, transaction_id)?;
```

Само имя подчёркивает, что это продвинутый путь для явной работы с `Plan`, а не обычный прикладной способ записи.

### Сессия теперь проверяет происхождение намерения

`SessionDatabase` при `preview`, `commit` и `commit_plan` проверяет, что переданное намерение создано под той же властью сессии.

Это важно не только для красоты интерфейса. Объект, который явно назван точкой публикации, теперь действительно является проверяемой границей полномочий.

## Что пока остаётся неудобным

P354 намеренно не объявляет проблему DX закрытой.

Самый заметный оставшийся шов:

```rust
let todos = tx.objects::<Todo>()?;
tx.add_plan(todos.insert(todo)?)?;
```

Для обычной записи здесь виден `Plan`, хотя прикладной разработчик хочет выразить только:

> добавить этот `Todo` в множество `Todo` внутри данной атомарной операции.

Это следующий приоритет.

## Целевая модель записи

Для обычного кода `Plan` должен стать внутренним представлением, а не обязательным элементом синтаксиса.

Минимально универсальная форма без сгенерированных имён коллекций может выглядеть так:

```rust
let mut tx = db.transaction()?;

db.objects::<User>()?.add(&mut tx, User {
    id: Id::new(1),
    name: "Artem".into(),
})?;

db.objects::<Project>()?.remove(&mut tx, project_id)?;

db.commit(&tx)?;
```

Здесь каждая строка показывает:

- базу;
- множество сущностей;
- транзакцию;
- конкретное изменение.

После появления типизированного фасада схемы желаемая форма ещё проще:

```rust
let mut tx = db.transaction()?;

db.users.add(&mut tx, User::new(...))?;
db.projects.remove(&mut tx, project_id)?;

db.commit(&tx)?;
```

Для одной простой операции может существовать сахар без явной транзакции, если его семантика остаётся одной точной атомарной публикацией:

```rust
db.users.add(User::new(...))?;
```

Но такой сахар не должен создавать скрытые многооперационные буферы внутри `Database` и не должен превращать базу в неявный `ChangeTracker`.

## Почему не копировать EF Core буквально

Удобство `DbSet.Add` и `SaveChanges` полезно как ориентир, но CFMD не обязана принимать скрытое отслеживание изменяемых объектов.

Нам важно сохранить:

- неизменяемые зафиксированные ревизии;
- точный `Plan` как внутреннее описание изменения;
- предварительно вычислимый будущий мир;
- идемпотентную публикацию;
- отсутствие скрытого запроса при чтении поля;
- отсутствие неявного повторного чтения новой HEAD-ревизии;
- точные дельты для `watch`.

Следовательно, цель — простота уровня `db.users.add(...)`, но без неявной изменяемой магии.

## Чтение и запросы

У чтения есть два естественных объекта власти:

- живая `Database`, если разработчику нужен текущий мир;
- конкретный `ReadContext`, если нужна зафиксированная ревизия.

Низкоуровневый `Query` должен оставаться описанием вопроса. Для обычного объектного интерфейса допустима цепочка, если её начало явно показывает источник:

```rust
let users = db.users
    .where_(|u| u.age().greater_than_or_equal(18))
    .all()?;
```

Если запрос сохраняется отдельно и позже выполняется, должен существовать явный вариант с точкой выполнения:

```rust
let query = /* описание */;
let users = db.execute(&query)?;
```

Для исторического мира аналогично:

```rust
let old = db.at(revision)?;
let users = old.execute(&query)?;
```

Задача следующих DX-проходов — привести объектный язык к этому правилу без дублирования двух разных механизмов запросов.

## Предварительный просмотр

Предварительный просмотр — операция над конкретной базой и конкретным намерением:

```rust
let preview = db.preview(&tx)?;
```

Из самой строки ясно:

- чей будущий мир рассматривается;
- какое изменение рассматривается;
- что публикации ещё не произошло.

`CandidatePreview` остаётся обычным значением результата. Он не должен сам менять базу.

## История и отмена

История принадлежит базе или конкретной исторической точке.

Желаемая модель:

```rust
let history = db.history()?;
let undo = history.transaction(id).undo()?;
let preview = db.preview(&undo)?;
db.commit(&undo)?;
```

Если `undo` в будущем станет отдельным типом намерения, принцип остаётся тем же: история создаёт описание обратного изменения, база публикует его.

## Подписки

После создания подписки `Watch` может иметь собственные операции жизненного цикла:

```rust
let mut watch = db.watch(&query)?;
let event = watch.next().await?;
watch.close();
```

Это не нарушает правило управления, потому что `next` и `close` не публикуют изменения в базу. Они управляют только уже созданной подпиской.

При этом создание подписки в конечной модели также желательно якорить на базе или на объектном наборе, который явно принадлежит базе.

## Разделение обычного и продвинутого интерфейса

Обычный прикладной разработчик должен в основном видеть:

```text
Database
Schema / типы сущностей
наборы сущностей
Query
Transaction
History
Watch
```

В нормальном CRUD ему не должны быть нужны:

```text
Plan
Candidate
RelationId
QueryNode
ручной TransactionId
внутренние отношения Γ
```

Эти примитивы остаются важны для:

- инструментов;
- Studio;
- протокола;
- языковых привязок;
- сложного предварительного анализа;
- низкоуровневых оптимизаций;
- отладки;
- специальных сценариев идемпотентности.

## Критерии хорошего DX для CFMD

Перед добавлением нового публичного метода надо проверить:

1. Видно ли из строки, над какой базой или ревизией выполняется действие?
2. Видно ли, что именно читается или меняется?
3. Отличается ли описание намерения от фактической публикации?
4. Может ли пассивное значение внезапно изменить живую базу?
5. Надо ли разработчику знать `Plan`, чтобы сделать обычный CRUD?
6. Требуется ли помнить скрытые ссылки на родительские объекты, чтобы понять строку?
7. Можно ли понять код локально, не переходя к месту создания нескольких промежуточных объектов?
8. Остаётся ли низкоуровневая строгая семантика CFMD единственным источником истины?

Если ответы плохие, интерфейс надо менять, даже если внутренне он уже работает правильно.

## Последовательность следующих проходов

### Следующий проход: запись сущностей без ручного `Plan`

Цель — обычные `add/insert`, `update`, `remove`, изменения отношений и массовые операции должны напрямую добавляться в явно указанную транзакцию через набор сущностей, а `Plan` строиться внутри.

### Затем: запросы

Нужно проверить каждую форму `where_`, `select`, переходы по отношениям, `one/all/count`, сохранённые запросы и выполнение на исторической ревизии. Приоритет — локальная читаемость и отсутствие скрытой смены источника данных.

### Затем: история и предварительный будущий мир

`History`, отмена, повтор, `Candidate`, предварительный просмотр и конфликтные сценарии должны подчиняться той же модели власти.

### Затем: подписки и асинхронность

Сам механизм уже силён. Задача DX-прохода — сделать создание и потребление подписок таким же очевидным по источнику, не меняя точную дельта-семантику.

### Затем: итоговый внешний аудит

После этих проходов надо написать небольшое реальное приложение только через `cfmd` и проверить, сколько раз обычному разработчику пришлось увидеть низкоуровневый примитив. Если `Plan`, `Candidate`, `RelationId` и внутренний runtime регулярно появляются в обычном коде, продуктовый фасад ещё не закончен.

## Итог P354

P354 не пытается скрыть сложность ядра косметическими именами. Он меняет направление управления:

```text
раньше:
Database -> Transaction -> Transaction.commit()

теперь:
Database -> Transaction
Database.preview(Transaction)
Database.commit(Transaction)
```

Это первая часть более крупного рефакторинга внешнего DX. Следующая часть должна убрать ручную прокладку `Plan` из обычной записи сущностей.

### Hosted/binding idempotency после P458

На transport boundary больше нет отдельного понятия `transaction: u128`: публичный DTO использует `IdempotencyKey`, который понижается в тот же durable `TransactionId`, что и локальный `Transaction::with_idempotency_key(...)`. Wire v2 при этом не меняется побайтно: key всё ещё кодируется фиксированным `u128`.

Повтор потерянного ответа после успешного remote commit обязан работать даже при уже устаревшем `base_revision`: identical key + exact relation effect возвращает `AlreadyCommitted`, changed effect под тем же key — `TransactionConflict`. Неизвестный stale intent не исполняется заново на новом HEAD и остаётся `StaleRevision`. Это намеренно отделяет безопасный durable retry от будущей задачи transport/rebase нового stale intent.
