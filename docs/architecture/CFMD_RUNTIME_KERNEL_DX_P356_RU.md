# CFMD P356 — Сведение внешнего DX с математикой ядра

## 1. Итог

Главная цель дальнейшей продуктовой линии: разработчик должен видеть простую предметную модель, а ядро — автоматически использовать максимально сильный доказуемый путь исполнения.

Целевой обычный код:

```rust
let mut tx = Transaction::new();

db.users.add(&mut tx, user)?;
db.orders.remove(&mut tx, order_id)?;

let preview = db.preview(&tx)?;
db.commit(&tx)?;
```

Пользователь не должен вручную выбирать между повторным применением, переносом, слиянием, residual-нормализацией, причинными идеалами или координацией. Эти понятия остаются внутренним механизмом и продвинутой диагностикой.

## 2. Что показал аудит kernel-change

`kernel-change` уже содержит существенно более сильную модель, чем прежний продуктовый `HEAD != base_revision -> StaleRevision`:

- семантические координаты записи;
- закон действия над координатой (`EnsurePresent`, `EnsureAbsent`, идемпотентное присваивание, коммутативное сложение, непрозрачное действие);
- классификацию пары намерений: сильная коммутативность, одинаковое идемпотентное намерение, доказанный конфликт, необходимость координации;
- причинные идеалы эффектов;
- residual-диаманты и кубы;
- конечную braid-нормализацию конкурентных переписываний;
- реестр семейств residual/sequential законов.

Следствие: глобальная ревизия не должна быть универсальным критерием жизнеспособности обычной транзакции.

## 3. Что показал аудит kernel-query

`kernel-query` уже работает не как «пересчитать запрос после записи», а как поддерживаемое точное состояние:

- точные дельты;
- семантическое равенство и порядок;
- поддерживаемые join/group/distinct/top-k;
- dependency-frontier;
- точные переходы maintained state;
- проверка эквивалентности инкрементального результата с семантическим результатом.

Поэтому внешний DX не должен заставлять приложение самостоятельно думать о пересчёте, инвалидировании или маршрутизации изменения. Запрос описывает интерес, runtime знает его зависимости, а `watch` получает только наблюдаемые изменения.

## 4. Что показал аудит kernel-plan/runtime

До P355/P356 runtime при переносе пользовательского намерения в основном использовал множество затронутых координат. Это позволяло доказать независимость разных координат, но теряло более сильный закон действия.

P356 меняет этот мост: runtime-history footprint теперь хранит для точной координаты не только факт записи, но и `RewriteActionLaw`.

Это позволяет различать:

- независимые координаты — перенос без координации;
- `EnsurePresent + EnsurePresent` — совместимое идемпотентное намерение;
- `EnsurePresent + EnsureAbsent` — доказанный конфликт;
- непрозрачное пересечение — требуется координация, fail-closed.

## 5. Почему нельзя механически объявить все вставки `EnsurePresent`

Hostile-регрессия P356 нашла два важных контрпримера.

### 5.1 Bag

Для множества класс либо присутствует, либо отсутствует. Для bag важна кратность. Две вставки одного Γ-класса означают не «обе гарантируют присутствие», а изменение кратности.

До появления точного закона коммутативного изменения кратности bag-класс остаётся `Opaque` при пересечении.

### 5.2 Один `Id`, разное содержимое

Две транзакции могут независимо создать сущность с одним и тем же `Id`, но разными полями. Само наличие carrier/lifecycle может выглядеть одинаково, однако payload конфликтует.

Поэтому членство конкретной сущности в carrier пока остаётся coordination-required. Чтобы снять этот консерватизм, runtime должен получить явный identity→payload law, а не угадывать его по соседним эффектам.

## 6. Что уже улучшено P356

Ранее два первых объекта одного типа могли ложно конфликтовать из-за общей координаты «carrier существует».

Теперь две вставки разных `Id` в ранее пустой тип корректно проходят как переносимые: обе требуют одного и того же `EnsurePresent` для carrier, но дальнейшие координаты различны.

Одновременно две вставки одного `Id` с различным состоянием по-прежнему конфликтуют/требуют координации.

## 7. Почему undo использует более строгую модель

Для прямого переноса намерения одинаковые идемпотентные действия могут быть совместимы.

Для исторического undo это не всегда верно. Если историческая операция создала факт, а более поздняя независимая транзакция снова выразила намерение «этот факт должен присутствовать», механическое удаление при undo затёрло бы более позднее намерение.

Поэтому P356 не заменяет все проверки истории одним общим merge-классификатором. Семантика прямого переноса и семантика обратного исторического эффекта остаются различными.

## 8. Целевая роль Transaction

Целевая `Transaction` — пассивное атомарное намерение, а не дочерняя база и не снимок мира.

Обычный режим:

```rust
let mut tx = Transaction::new();
```

Строго временно привязанный режим:

```rust
let snapshot = db.snapshot()?;
let mut tx = Transaction::from(snapshot);
```

В обычной транзакции ревизия не должна быть её сущностью. Отдельные операции могут нести доказательные предпосылки, если их смысл действительно зависел от чтения конкретного состояния.

## 9. Целевая роль Database

`Database` остаётся объектом власти.

```rust
db.preview(&tx)?;
db.commit(&tx)?;
```

Именно БД:

1. получает текущий причинный мир;
2. сопоставляет его с намерением;
3. использует kernel-change для классификации;
4. применяет координационно-свободные действия напрямую;
5. использует зарегистрированный residual-закон там, где он существует;
6. только при невозможности доказать корректное продолжение возвращает конфликт.

## 10. Что разработчик не должен видеть в обычном пути

Необязательны для обычного CRUD:

- `Plan`;
- Γ-координаты;
- residual certificates;
- causal ideals;
- идентификаторы внутренних rewrite-law семейств;
- `TransactionReadiness` как обязательный шаг;
- ручной rebase.

Они остаются для Studio, диагностики, протокола, расширений и низкоуровневого API.

## 11. Что ещё мешает автоматическому `db.commit(&tx)`

Главный оставшийся фундаментальный блокер — долговечная идентичность намерения.

Сейчас durable idempotency сравнивает конкретный `DurableTransactionIntent`, в который входят source/target revision. Если старое намерение доказанно переносится на новый HEAD, его конкретная переходная пара меняется.

Нельзя допустить, чтобы повтор после потерянного ответа породил второе применение того же исходного намерения.

Поэтому до автоматического merge-commit необходимо ввести стабильную идентичность исходного семантического намерения, независимую от конкретного HEAD, на который оно было перенесено.

## 12. Следующая архитектурная лестница

Обычный `db.commit(&tx)` должен в перспективе выполнять под капотом:

1. проверить уже опубликованный стабильный идентификатор намерения;
2. если намерение уже опубликовано — вернуть тот же результат;
3. если HEAD совместим напрямую — применить;
4. если изменения сильно коммутируют — перенести;
5. если намерения одинаково идемпотентны — схлопнуть корректно;
6. если нужен residual и зарегистрирован точный закон — построить сертифицированный residual;
7. если есть доказанный конфликт — вернуть предметную диагностику;
8. если математика недостаточна — требовать координации/fail-closed, но не использовать generic fallback.

## 13. Ближайшие шаги

### P357

Ввести transport/durability-stable identity исходного transaction intent. Она не должна зависеть от конкретного source/target revision после сертифицированного переноса.

### P358

Подключить automatic certified commit для `StrongCommute` и `SameIdempotentIntent`, сохраняя exact retry/recovery.

### P359+

Подключать residual merge только для тех семейств действий, для которых kernel-change действительно имеет зарегистрированный закон и сертификат. Не вводить универсальный эвристический merge.

### После merge-runtime

Только после этого окончательно упростить внешний CRUD:

```rust
let mut tx = Transaction::new();
db.users.add(&mut tx, user)?;
db.commit(&tx)?;
```

и убрать `Plan` из обычной пользовательской записи.
